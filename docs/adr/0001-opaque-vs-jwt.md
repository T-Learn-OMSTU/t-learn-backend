# ADR-0001: Opaque-токены вместо JWT для аутентификации

## Статус

`proposed`, 2026-11-18

## Контекст и постановка проблемы

Необходимо выбрать формат токенов для аутентификации пользователей. Ключевые ограничения:

1. Проект разрабатывается как монолит - преимущества stateless-проверки для микросервисов неприменимы.
2. ТЗ требует повторную авторизацию пользователя раз в 30 дней - нужен фиксированный TTL сессии.
3. В системе используется кэширование, стоимость проверки токена - одна операция чтения.

**Проблема:** JWT или Opaque?

## Рассматриваемые варианты

### JWT

**Плюсы:**

1. Stateless-проверка access-токена - любой микросервис может самостоятельно проверить подпись.
2. Масштабируемость - нет зависимости от общего хранилища сессий.
3. Данные доступны прямо в payload без обращения к хранилищу.

**Минусы:**

1. Нельзя мгновенно отозвать токен до истечения TTL.
2. Большой размер токена (заголовок, полезная нагрузка, подпись).
3. Больше криптографии (генерация и проверка подписи).

### Opaque-токены

**Плюсы:**

1. Мгновенный отзыв - удаление записи из хранилища.
2. Простота - минимум криптографии, случайная строка.
3. Непрозрачность - клиент не видит содержимое сессии.

**Минусы:**

1. Запрос к хранилищу на каждый вызов.
2. Кэш становится единой точкой отказа.
3. Сложнее в микросервисной архитектуре (не актуально в текущем контексте).

## Решение

Используем один Opaque-токен с фиксированным TTL 30 дней.

Обоснование:

1. **JWT без пары access/refresh не имеет смысла:** при коротком TTL страдает UX, при длительном - токен невозможно отозвать весь срок жизни.
2. **JWT с парой access/refresh теряет главное преимущество - stateless:** для refresh всё равно нужно ходить в хранилище, а экономия на проверке access - всего одна проверка кэша.
3. **Требование "TTL токена авторизации 30 дней" не позволяет организовать ротацию refresh-токенов:** если выдавать новый refresh при каждом использовании, сессия постоянно активного пользователя никогда не истечёт и фиксированный TTL установить не выйдет. А refresh без ротации не дает существенных преимуществ перед одним токеном с фиксированным TTL - в таком случае получение этого refresh позволит получать по нему новые access весь TTL.
4. **По скорости Opaque не проигрывает JWT в нашем контексте:** разница - один поход в кэш.
5. Монолитная архитектура снимает аргумент масштабируемости JWT.

## Последствия

### Положительные

* **Мгновенный отзыв:** Блокировка/выход пользователя - это удаление ключа из кэша.
* **Простота реализации:** генерация криптографически стойкой случайной строки, без работы с подписями и ключами.
* **Актуальность данных:** данные сессии читаются из хранилища на каждый запрос и всегда свежие.
* **Соответствие ТЗ:** TTL сессии фиксирован - ровно 30 дней, как и требует ТЗ.

### Отрицательные

* **Зависимость от кэша:** недоступность кэша = недоступность аутентификации (единая точка отказа).
* **Проверка кэша на каждый запрос:** дополнительная нагрузка на кэш.
* **При переходе к микросервисной архитектуре:** потребуется либо общий доступ к кэш-машине, либо переход на JWT.
